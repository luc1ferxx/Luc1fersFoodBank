# Honest Boundaries

This project is intentionally strong on backend correctness patterns, but it is still a demo application:

- Payment is simulated with local request validation. There is no real payment provider, authorization, capture, webhook, or settlement flow. The recorded capture (`SIMPAY-...`) and the refunds (`SimulatedRefundGateway`, which always succeeds after its configured failures) are simulated the same way.
- After-sales is refund-only: no returns, replacements or vouchers, one answer per restaurant per request, and at most two requests per order. A customer can still cancel an `ACCEPTED` order after the rider picked it up; that cancel refunds only a share (50% by default), and a cancel in the moment between the pickup and its event reaching the order module (the outbox delay) is still refunded in full (ADR 0002 section 27, follow-up 17).
- Timestamps, after-sales deadlines included, carry no offset in the API: they are UTC by convention (the server runs in UTC and the UI reads them as UTC, see "Timestamps and time zone"), not by type. Rows a server wrote in another zone before keep that zone's wall-clock time.
- There is no inventory reservation or stock decrement model.
- Amounts carry their currency, but there is no conversion: a restaurant prices in one currency and a cart or order stays in it. There are no taxes, discounts or tips, and no currencies with three minor digits.
- Pushed updates are change signals, not data, and best effort: a signal lost to a Redis outage or a reconnect shows up with the next fallback poll (every 60 seconds while the stream is open, 15 seconds without it). The stream limits are per instance, a stream opened before a logout keeps receiving signals (no data) until its client closes it or its 30-minute timeout, and the rider console has no map, location, or ETA. The customer's order list does not poll: it and the refund cases are read again when a notification read brings a new notification, so with notifications neither pushed nor polled a newly completed order shows "Request a refund" only after Refresh or after the page is shown again.
- Kafka delivery is treated as at-least-once with consumer-side idempotency, not end-to-end exactly-once delivery. The
  outbox keeps each aggregate's events in order on their way to Kafka, so one `FAILED` event stops its order until an
  operator retries it, or abandons it and reconciles what its consumers missed.
- Event schemas live in the repository (`event-schemas/`); there is no schema registry service.
- Failed outbox rows require explicit admin retry after the underlying cause is fixed.
- H2 is a lightweight local fallback, not the production-shaped runtime.
- With read replicas on, a user sees other users' changes (a merchant's accept, a notification) up to `max-lag` (2s) late, a session's reads can go back by up to that much when its replica drops out and it moves to another, and a read that is running on a replica when it dies fails instead of being retried on the primary.
- Catalog edits are limited to admin updates of existing restaurants and menu items. There is no create or delete API, so rows changed directly in the database show up once the cached entries expire. One exception: `GET /restaurant/{id}/menu` serves a directly inserted restaurant at once and evicts the stale list, because an id missing from the cached list is checked in the database (rate-limited) before the `404`. The demo seed matches rows by name, so renaming a demo restaurant or item makes the next startup with `db/demo` insert the original again.
- The architecture is a deliberate monolith. Service decomposition is deferred until the core transaction is correct and observable.
- The order data lives in one PostgreSQL database; sharding is planned ([ADR 0001](adr/0001-order-sharding.md)), not built. Customers see only the public `order_no` (order history, checkout confirmation, notifications; the admin order tool shows both). The merchant and rider consoles show it too, from the copy the merchant inbox and the deliveries take from the order events (v2, V14), but rows from before V14 (and rows that only v1 events reached during the rollout) have none and still show the internal `id`; nothing backfills them, since the fulfilment modules never read `orders` (an optional one-off backfill of the open rows is in [docs/operations.md](operations.md) section 8).
